## A. CONSISTENCIA

1. [ALTA] La exclusión de Fases 3 y 4 no cubre los dos mockups — El alcance nominal del plan coincide con la Fase 2 (home, categoría, búsqueda, PDP, reviews y tags), pero la frontera operativa solo advierte que `producto.html` contiene configurador y add-to-cart. `index.html` también contiene navegación a Bundles y checkout, discurso de bundles, un producto Bundle, un configurador completo y un CTA “Agregar combo al carrito”. Además, `producto.html` incluye cross-sell “Combina con tu Brent”, que puede inducir a crear la compatibilidad curada reservada para Fase 3. “Excluir o stubbear” tampoco define si deben desaparecer, quedar visualmente inertes o reemplazarse por contenido de Fase 2; un control de carrito falso o un CTA muerto no es un resultado aceptable. El plan debe incorporar una matriz por bloque de ambos mockups con `INCLUIR / EXCLUIR / REEMPLAZAR`, y excluir comportamiento de bundles, compatibilidad curada, cantidad, carrito y checkout. La moderación como estado de datos puede anticiparse aditivamente, pero su panel debe seguir fuera. — Evidencia: `PLAN-FASE-2-PLANNING.md:13-20`, `PLAN-FASE-2-PLANNING.md:56-59`, `PLAN-MAESTRO.md:78-102`, `mockups/index.html:303-321`, `mockups/index.html:346-366`, `mockups/index.html:389-397`, `mockups/index.html:420-440`, `mockups/producto.html:335-370`, `mockups/producto.html:428-437`.

## B. INSUMOS

2. [ALTA] El DTO actual contradice la invariante de disponibilidad y la task debe ordenar su reemplazo explícito — El plan detecta correctamente que la disponibilidad debe salir de `inStock`, pero el único DTO actual sigue publicando `stock` y no incluye `inStock` ni `salePriceCents`. Para un ejecutor que solo recibe tasks no alcanza con decir “extender el data layer”: la task debe fijar el DTO esperado, prohibir usar/exponer `stock` para UI y cubrir con tests las combinaciones `stock = 0, inStock = true`, `stock = 0, inStock = false`, precio promocional y `priceCents = 0`. — Evidencia: `PLAN-FASE-2-PLANNING.md:37-48`, `PLAN-FASE-2-PLANNING.md:61-66`, `prisma/schema.prisma:45-57`, `src/lib/data/products.ts:5-17`, `src/lib/data/products.ts:34-43`.

3. [MEDIA] Faltan invariantes del schema que afectan directamente los cambios aditivos — El plan recoge centavos, disponibilidad y lazy Prisma, pero omite trasladar a spec/tasks que `material` y `sizeMm` son strings libres, no enums; que los timestamps usan `timestamptz`; y que `slug` y `sku` siguen siendo las claves de upsert, mientras `wooId` es solo provenance. Esto importa para no convertir los selectores en una matriz de enums rígida, para que `Review` conserve la convención temporal y para que agregar tags/campos de categoría no altere identidad ni importabilidad. También debe conservarse `trailingSlash: true` al definir URLs y enlaces de PDP/categoría. — Evidencia: `prisma/schema.prisma:12-17`, `prisma/schema.prisma:23-26`, `prisma/schema.prisma:46-48`, `prisma/schema.prisma:58-65`, `next.config.ts:26-29`, `PLAN-FASE-2-PLANNING.md:68-72`.

4. [MEDIA] La extensión del data layer no tiene contrato de errores ni de resultados vacíos — La implementación actual solo hace un `findMany` ordenado y la home propaga fallas porque también funciona como healthcheck. Las nuevas funciones por slug, categoría y búsqueda necesitan distinguir “no existe” de “DB falló”, definir orden estable y paginación, y no devolver instancias Prisma a Client Components. Sin ese contrato, el ejecutor puede convertir errores en 404/empty-state o introducir resultados no deterministas. — Evidencia: `src/lib/data/products.ts:19-32`, `src/app/(shop)/page.tsx:8-19`, `src/lib/db.ts:34-44`, `PLAN-FASE-2-PLANNING.md:61-66`.

## C. RIESGOS TÉCNICOS

5. [ALTA] El conflicto de caché está identificado, pero falta resolver el tercer vértice: `next build` sin DB — Mover el healthcheck a `/api/health` es una buena separación de responsabilidades, pero no basta para volver cacheable el catálogo. Tanto prerender/ISR como un `use cache` evaluado durante prerender pueden ejecutar consultas en build, mientras el repositorio exige que importar rutas y correr `next build` funcione sin `DATABASE_URL`. El design debe elegir y demostrar un patrón concreto: por ejemplo, shell estático más consulta diferida a request con `Suspense`/`connection()` y caché runtime, o cambiar explícitamente el contrato de CI para disponer de DB. Con Cache Components, `dynamic = "force-dynamic"` deja de ser la herramienta de control; no se deben mezclar configuraciones de ISR clásico y Cache Components. La ruta de health debe consultar la DB de forma barata, no cacheada, devolver non-2xx ante fallo y cambiarse en Coolify solo después de desplegarla. Criterios obligatorios: `npm run build` sin DB, health con DB viva/caída, headers de caché reales y comportamiento tras reinicio/revalidación. — Evidencia: `PLAN-FASE-2-PLANNING.md:74-78`, `PLAN-FASE-2-PLANNING.md:98-108`, `src/lib/db.ts:34-39`, `src/app/(shop)/page.tsx:4-13`, `next.config.ts:26-47`, `PERFORMANCE.md:47-50`. Contraste primario: [Next.js 16 Cache Components](https://nextjs.org/docs/app/getting-started/partial-prerendering), [Next.js `connection()`](https://nextjs.org/docs/app/api-reference/functions/connection), [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers).

6. [ALTA] El contrato de imágenes dice `fill` “o” `sizes`, y eso es técnicamente incorrecto — Como las URLs remotas no aportan dimensiones, cada imagen necesita `width`+`height` conocidos o `fill`; `sizes` no reemplaza dimensiones. Cuando se usa `fill`, el contenedor debe reservar geometría/ser posicionado y además debe informarse `sizes`, o el navegador asume 100vw y descarga variantes sobredimensionadas. También falta trasladar el requisito LCP a la versión instalada: en Next 16 se usa `preload` (la prop `priority` está deprecada), mientras el resto queda lazy. Las tasks deben fijar contratos por slot (hero, primera imagen PDP, thumbnails, cards), `alt`, aspect ratio, `sizes`, `preload` y ausencia de CLS. — Evidencia: `PLAN-FASE-2-PLANNING.md:43-46`, `prisma/schema.prisma:79-90`, `next.config.ts:31-37`, `PERFORMANCE.md:27-31`, `package.json:20-26`. Contraste primario: [Next.js 16 Image](https://nextjs.org/docs/app/api-reference/components/image).

7. [ALTA] El modelo Review no define un ciclo de vida utilizable en Fase 2 — El enum de moderación es correcto y evita un boolean ambiguo, pero faltan decisiones que cambian el producto y la seguridad: `PENDING` como default; `rating` protegido por CHECK real de DB (Prisma no lo expresa solo con `Int`, por lo que exige SQL de migración); `email` nunca expuesto por el DTO público; relación y borrado con Product; y si Fase 2 permite enviar reviews o solamente muestra APPROVED. Si permite envío, hacen falta validación server-side, límites de longitud, anti-abuso/rate limiting y estados de éxito/error; si solo lee, hacen falta empty-state y un mecanismo explícito para disponer de reviews aprobadas sin adelantar el panel de Fase 5. Dejar esto implícito produce una UI siempre vacía o abre un endpoint público sin controles. — Evidencia: `PLAN-FASE-2-PLANNING.md:127-135`, `PLAN-FASE-2-PLANNING.md:94`, `PLAN-MAESTRO.md:78-82`, `PLAN-MAESTRO.md:98-102`, `mockups/producto.html:410-423`. Contraste primario: [Prisma y CHECK constraints](https://docs.prisma.io/docs/orm/more/troubleshooting/check-constraints).

8. [MEDIA] FTS + `unaccent` + `pg_trgm` no debe convertirse en requisito por defecto — Para 88 productos, el propio plan reconoce que `ILIKE` puede alcanzar. La decisión debe partir de un contrato observable — campos buscados, normalización de acentos/caso, mínimo y máximo de query, typo tolerance deseada, orden/ranking, paginación, query vacía y tiempo objetivo — y elegir la solución más simple que lo cumpla. Si se eligen extensiones, las tasks deben contemplar migración SQL aditiva, disponibilidad de extensiones en el Postgres objetivo, índice compatible, consultas parametrizadas y prueba de rollback/drift; Prisma no vuelve automáticamente type-safe los operadores de extensión. — Evidencia: `PLAN-FASE-2-PLANNING.md:119-125`, `prisma/schema.prisma:5-10`, `src/lib/data/products.ts:24-32`, `tasks/todo.md:53-60`. Contraste primario: [Prisma PostgreSQL extensions](https://docs.prisma.io/docs/postgres/database/postgres-extensions).

## D. PROCESO

9. [ALTA] El gate de design está escrito en una secuencia que permite crear tasks antes de aprobarlo — El paso 2 dice continuar hasta completar `spec → design → tasks` y recién en el subpunto menciona aprobación del design. La secuencia vinculante debe ser `proposal → GATE → spec → design → GATE → tasks`; tras producir design, la sesión debe detenerse y no invocar la fase de tasks hasta tener aprobación registrada. El gate de proposal sí está ubicado inequívocamente. — Evidencia: `PLAN-FASE-2-PLANNING.md:22-30`.

10. [ALTA] La verificación de planning prueba existencia, no consistencia ni cobertura — La sección actual verifica observaciones, aprobaciones, actualización de TODO y que las tasks nombren archivos/comandos, pero no exige: trazabilidad de cada requisito y exclusión hacia al menos una task; consistencia proposal/spec/design/tasks; registro de decisiones abiertas resueltas; validación de fuentes web primarias; dependencias y orden de ejecución; criterios negativos; ni una lectura final simulando al Opus sin memoria. “Output esperado” puede dar una falsa garantía si no se cubren fallos, migraciones, build sin DB, accesibilidad y recorrido real. Debe agregarse un gate documental de trazabilidad y completitud antes del cierre. — Evidencia: `PLAN-FASE-2-PLANNING.md:28-30`, `PLAN-FASE-2-PLANNING.md:96-103`, `PLAN-FASE-2-PLANNING.md:144-151`.

11. [MEDIA] “El ejecutor usa solo las tasks” necesita una regla de autosuficiencia verificable — Es razonable que las tasks sean el artefacto de handoff, pero deben incluir o referenciar de forma inmutable los IDs aprobados de spec/design y repetir todas las invariantes necesarias para ejecutar, no solo paths y comandos felices. Cada task debería declarar precondiciones, archivos permitidos, dependencias, comportamiento esperado, casos de error, pruebas, verificación manual y lo que queda fuera. Si cualquier decisión necesaria solo vive en conversación, explore o design, el handoff incumple su propio contrato. — Evidencia: `PLAN-FASE-2-PLANNING.md:24-33`, `PLAN-FASE-2-PLANNING.md:146-151`, `src/lib/db.ts:25-39`, `prisma/schema.prisma:12-17`.

Esto impide que la fidelidad visual arrastre Bundles, cart, checkout, compatibilidades o promesas funcionales falsas. — Evidencia: `mockups/index.html:346-366`, `mockups/index.html:420-440`, `mockups/producto.html:335-370`, `PLAN-MAESTRO.md:84-96`.

13. [ALTA] Agregar una tabla de decisiones técnicas con prueba de aceptación — Como mínimo: estrategia de render/cache y build sin DB; contrato de `/api/health`; lifecycle de Review; búsqueda; DTOs/paginación; y estrategia de imágenes. Cada fila debe tener decisión, alternativa descartada, consecuencia, task responsable y comando o verificación observable. Esto convierte riesgos hoy narrativos en insumos ejecutables. — Evidencia: `PLAN-FASE-2-PLANNING.md:61-86`, `PLAN-FASE-2-PLANNING.md:98-140`.

14. [MEDIA] Agregar una matriz `requisito → task → evidencia` — Debe cubrir también requisitos negativos (`priceCents = 0` nunca es gratis, `stock` nunca decide disponibilidad, no Fases 3-6, no DB en build) y verificaciones manuales responsive/accesibles. Es la forma directa de demostrar que un ejecutor sin memoria puede cumplir la spec sin perder restricciones. — Evidencia: `PLAN-FASE-2-PLANNING.md:37-48`, `PLAN-FASE-2-PLANNING.md:80-94`, `PLAN-FASE-2-PLANNING.md:144-151`.

## Veredicto

**APROBAR CON CAMBIOS.**

Antes de ejecutar `sdd-new fase-2-pdp`, deben incorporarse estos cambios:

1. Delimitar ambos mockups con una matriz explícita y sacar de Fase 2 bundles, compatibilidad curada, cantidad, carrito y checkout.
2. Convertir el conflicto de caché en una decisión que preserve `next build` sin DB, separe un healthcheck no cacheado y exija pruebas de headers/revalidación.
3. Corregir el contrato de `next/image` a dimensiones o `fill` **más** `sizes`, con `preload` solo en LCP y geometría reservada.
4. Definir el ciclo de Review, incluyendo default de moderación, CHECK de rating, privacidad del email y alcance lectura/escritura.
5. Incorporar al handoff las invariantes de DTO/schema/URLs y un contrato observable para búsqueda, paginación, errores y empty states.
6. Reescribir la secuencia para que el gate de design ocurra antes de tasks y cerrar el planning con trazabilidad completa requisito → task → evidencia.

No corresponde rechazar el plan porque el núcleo de Fase 2 y las fases diferidas están identificados; sí corresponde impedir su ejecución en el estado actual porque las ambigüedades señaladas pueden producir scope creep y un handoff técnicamente incompleto.
